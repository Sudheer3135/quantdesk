# QuantDesk's public HTTPS site

One Caddy server on the existing Azure VM. It asks the owner to sign in,
serves the compiled dashboard, and forwards the dashboard's GET requests to
the API that already runs on `127.0.0.1:8000`.

```
browser ── HTTPS ──▶ Caddy :443 ── sign-in (HTTP Basic, bcrypt hash)
                        ├── /            compiled dashboard, /srv/quantdesk/web
                        ├── /api/<route> ─▶ 127.0.0.1:8000/<route>    16 GET routes
                        └── /api/ws/signals (same origin only)
                                         ─▶ 127.0.0.1:8000/ws/signals?key=…   key added here
```

Nothing about the desk itself changes: the same single `quantdesk-api`
process owns the scheduler, the Angel feed and the paper engine; PostgreSQL
and Redis stay on loopback; port 8000 is never opened. There is no second API,
scheduler or feed, and no anonymous access. The browser talks to one origin:
the dashboard at `/`, its requests under `/api/`, the stream at
`/api/ws/signals`.

**Caddy 2.11.7**, the stock build from Caddy's own apt repository — no plugins,
no custom build. The number lives in `CADDY_VERSION`: `install_caddy.sh`
installs exactly that release, in CI and for the first install on the VM, the
tests run against it, and `install.sh` deploys onto exactly that release and
no other. Ubuntu's own package (2.6.2) is not used and does not read this
Caddyfile. The package is not held at 2.11.7 afterwards; see "Caddy updates".

| File | Becomes on the VM |
|---|---|
| `CADDY_VERSION` | the Caddy release this is written for and CI tests |
| `install_caddy.sh` | installs that release, stopped and disabled |
| `check_caddy_updates.sh` | read-only: evidence about Caddy updates, not a verdict |
| `certificate_authority.sh` | read-only: the CA and certificate storage Caddy would really use |
| `clear_staging_trial.sh` | removes the staging trial's own storage directory, nothing else |
| `Caddyfile` | `/etc/caddy/Caddyfile` |
| `caddy.service.d/quantdesk.conf` | `/etc/systemd/system/caddy.service.d/quantdesk.conf` |
| `caddy.env.example` | template for `/etc/quantdesk/caddy.env` (root, mode 600) |
| `install.sh` | checks everything, then puts the dashboard and the two files above in place |
| `../build_web.sh` | the static build (`VITE_API_URL=/api`, no key) |

## What is reachable

Signed in, a browser can GET exactly the paths the dashboard itself requests
(`tests/test_public_proxy.py` fails if the two lists differ):

`/signals/live` `/signals/history` `/signals/outcomes` `/market/status`
`/market/price` `/market/regime` `/market/candles` `/market/candles/history`
`/market/option-chain` `/market/vix` `/v2/status` `/data/quality`
`/data/coverage` `/health/scheduler` `/health/feed` `/news`, and the live
stream `/ws/signals`.

GET is not the same as read-only, and one of these is not read-only:

**`/signals/live`** computes and serves the current signal. Each call runs the
API's existing analysis — market data, the option chain, the broker feed. It
cannot store a signal row from here: that needs the `persist` parameter,
which this proxy refuses in every spelling. But it **may commit methodology
holdout-exposure metadata**: serving a signal shows the strategy that session,
and when the session is protected holdout data the API's existing
`note_exposure()` safeguard records that it has now been seen. That write is
intended, is the record of the exposure, and is not blocked, suppressed or
changed by anything here. The owner opening the dashboard can therefore mark
a protected session as exposed, exactly as opening it over the SSH tunnel does
today.

Everything else answers 404 at the proxy and never reaches the API: the
journal, `POST /v2/close`, every `/backtest/*`, every import and backfill,
the research and readiness reports, `/docs` and `/openapi.json`.
Any `persist` parameter is refused, `/signals/live` takes only a query in
plain letters, digits and `_ = & . -`, and no `X-API-Key` a caller sends is
forwarded. Those routes stay where they are: over SSH.

This is the design as written and as the tests exercise it, not a finding
that it is safe. Still to be checked independently in review: what each of
the sixteen forwarded handlers does (side effects, calls to outside services,
expensive work, anything stored); how the proxy and the API each read a path
and a query; and that the key the proxy adds cannot surface in a log, an error
or a dump of Caddy's configuration.

## Secrets

- **Owner password.** One owner. The password is generated by a password
  manager: 32 random characters, unique to this site, never reused for Angel,
  the API key, SSH or anything else. It is never committed, never passed as a
  command argument, and never written on the VM. Only its hash is stored, in
  `/etc/quantdesk/caddy.env` (root, mode 600): bcrypt, cost 14, made by typing
  the password at the prompt of

      caddy hash-password --algorithm bcrypt --bcrypt-cost 14

  Both flags are given so the result does not depend on Caddy's defaults.
  `install.sh` refuses a hash that is not bcrypt of cost 14.
- **API key**: stays on the server. The compiled dashboard has none
  (`build_web.sh` refuses to build with one and searches its output for every
  `.env` value). Caddy adds it to the websocket request it forwards, read from
  its environment per request, so it is not written in the Caddyfile.
- **Logs**: see "Logging" below.

## Logging

The API key travels in the address of the websocket request Caddy sends to
the API (`/ws/signals?key=…`). Caddy replaces the value of sensitive headers
such as `Authorization` with `REDACTED` when it logs a request. That covers
headers. It says nothing about a key in an address, and is not the reason to
believe the key stays out of the logs.

What the tests show, on Caddy 2.11.7 at its normal log level, with made-up
credentials: the key does not appear in the access log or in Caddy's own log
when the stream opens and closes, when the API hangs up, answers with
something that is not HTTP, never answers, is not listening at all, or
answers 400, 401, 403, 404, 500 or 503; nor in what Caddy refuses itself;
nor in what it writes while shutting down with a stream open; nor in the
configuration it adapts or reports. That is a test result for the cases
tried, to be checked again in review, not a guarantee about every message
Caddy can write.

**Debug logging is different, and prohibited with production credentials.**
With Caddy's `debug` option on, its reverse proxy logs the address of every
request it forwards, key included. A test keeps that fact in view
(`test_debug_logging_does_write_the_key_…`), and another fails if `debug`
appears in the Caddyfile.

- **Production**: never enable `debug`, or a `debug` log level, on the Caddy
  that holds the real API key.
- **Troubleshooting**: if debug-level proxy logs are needed, run a separate
  Caddy and upstream — as the tests do — with made-up credentials. The real
  key is never debug-logged.
- **If debug was enabled in production**, treat the API key as potentially
  exposed, and in this order:
  1. turn debug off;
  2. restrict access to the logs it wrote (the journal, any copies);
  3. rotate the API key, coordinated: the project's `.env`, a restart of
     `quantdesk-api` at a time the desk can take one, then
     `/etc/quantdesk/caddy.env` and a restart of Caddy.

  Rotating the key while debug is still on is not a mitigation: the
  replacement is logged just the same.

## What protects the sign-in, and what does not

The site is on the open internet and three things stand in front of it: the
32-character random password, HTTP Basic authentication over HTTPS, and a CPU
cap on Caddy (`CPUQuota=50%`, `CPUWeight=20`). There is no rate limit, no
lock-out, no restriction by address and no second factor.

Checking a password against a cost-14 bcrypt hash is deliberately expensive,
on the order of a second of one core. Assume any request may cost that much.

The CPU cap is resource containment for the Caddy process only: at most half
of one core, and a small share when the VM is busy. It is not rate limiting
and not protection against denial of service of any kind. It does not bound
Caddy's memory, the number of connections, network traffic, or the work that
forwarded requests cause in the API. Someone sending enough traffic can still
make the dashboard unavailable, and nothing here guarantees that QuantDesk
stays available under attack.

## Safari

Not tested. Safari may not send the saved sign-in when it opens a websocket,
in which case the stream is refused (401) and the dashboard falls back to the
polling it already has. That is accepted for the first deployment, as a
degraded transport, only once a real Safari session has shown that signed-in
reads work, updates keep arriving, the fresh/stale indicators stay accurate
and reconnect attempts stay bounded. Nothing is loosened to avoid it: Basic
authentication and the origin check stay, no credential goes in a URL, and
polling intervals, freshness thresholds and the API are unchanged.

## Caddy updates

The first install is 2.11.7, the release reviewed and tested. The VM is not
held there: the package can be updated later, and after an update the running
Caddy is no longer the build these tests ran against. Do not assume it is.

- **Does the VM update Caddy by itself?** Not known, and not something a
  script here decides. Having Caddy's apt repository configured does not mean
  unattended-upgrades installs from it: that depends on how its origin
  patterns match the repository, on blacklists, holds and pins, and on
  whether it runs at all. `./scripts/native/caddy/check_caddy_updates.sh`
  gathers the evidence during the deployment review — versions, the
  repository's origin, the unattended-upgrades configuration, exclusions,
  timers and a dry run, with any failure shown as a failure. It is diagnostic
  evidence, not an authoritative evaluation of the policy: its verdict is
  always `UNKNOWN — MANUAL INTERPRETATION REQUIRED`. A person reads the
  evidence and records the conclusion. Until one has, assume Caddy security
  fixes arrive only when someone installs them. The unattended-upgrades
  policy itself is not changed by anything here.
- **Record every upgrade**: date, old and new version (`caddy version`).
- **When the version changes**, the routing, sign-in, origin and logging
  results above no longer describe the Caddy that is running: they are per
  release. Follow "If Caddy is not the reviewed version" below.
- **A running Caddy is left running.** A package update that moves the
  version is not a reason to stop it or to downgrade it, and nothing here
  does either. The exact-version rule is a gate on deploying, not a hold on
  the package: there is no `apt-mark hold` and no other pin.
- **What an update interrupts**: the package restarts `caddy.service`, which
  briefly drops the dashboard's HTTPS connections and its websocket (the
  dashboard reconnects or polls). It must not restart `quantdesk-api` — and
  with it the scheduler, the feed and the paper engine — PostgreSQL or Redis;
  none of them depends on Caddy. Confirm after any update that their start
  times did not move.

## If Caddy is not the reviewed version

`install.sh` deploys only onto the exact release in `CADDY_VERSION`
(2.11.7). Older or newer, it stops before it builds, writes or replaces
anything, and `install_caddy.sh` stops the same way rather than change a Caddy
that is already installed. There is no override. When that happens:

1. Stop. Nothing has been modified; do not work around the gate.
2. Record the installed version (`caddy version`) and how it came to differ.
3. Change `CADDY_VERSION` in the repository to that version, deliberately,
   as a reviewed change.
4. Run the whole of `tests/test_public_proxy.py` against that exact version
   (CI does, once `CADDY_VERSION` names it).
5. Run `caddy validate` on the Caddyfile and `certificate_authority.sh` for
   both production and staging against it.
6. Have the result reviewed again.
7. Only then resume the deployment.

Downgrading the VM's Caddy to make the numbers agree is not one of the steps
and is not done automatically by anything here.

## Hostname and certificate — the gate before going live

The site uses the Azure-provided DNS name of the VM's existing static public
IP (`<label>.<region>.cloudapp.azure.com`). **The label has not been chosen.**
Nothing can be deployed until it is supplied; no name is invented here.

Once it is, every item below is checked and written down before the site is
called live. A browser certificate warning is never an accepted state, and
neither is a staging, self-signed or internal certificate, or one from any
other CA.

**DNS**
- the name resolves to the VM's static public IP (`dig +short A <hostname>`,
  from outside Azure, against more than one resolver);
- there is no other address record for it: one A record, and no AAAA unless
  it also reaches this VM (`dig +short AAAA <hostname>`).

**Certificate authority: Let's Encrypt only**
- production: `https://acme-v02.api.letsencrypt.org/directory`
- staging, for the trial only:
  `https://acme-staging-v02.api.letsencrypt.org/directory`

Caddy's usual second authority (ZeroSSL) is deliberately given up: this first
deployment trades cross-CA fallback for a policy simple enough to review. In
staging mode staging is the only issuer — no production directory behind it,
no other CA. In production mode production is the only issuer.

That is checked on the configuration Caddy actually builds, not on the
Caddyfile's text:

    sudo ./scripts/native/caddy/certificate_authority.sh \
        --env-file /etc/quantdesk/caddy.env --require production /etc/caddy/Caddyfile

(`--require staging` during the trial.) It prints every effective issuer and
the effective certificate storage, and fails unless there is exactly one
issuer, it is the Let's Encrypt directory asked for, and it is kept in that
directory's own storage. `install.sh` runs the same check before it puts
anything in place.

**Two storage directories, never shared**

| | Let's Encrypt directory | Kept in |
|---|---|---|
| production | `acme-v02.api.letsencrypt.org` | `/var/lib/caddy/quantdesk/production` |
| staging trial | `acme-staging-v02.api.letsencrypt.org` | `/var/lib/caddy/quantdesk/staging-trial` |

The Caddyfile defines the two as fixed pairs, and `QUANTDESK_CERTIFICATES`
picks one: absent for production, `staging` for the trial. There is no
setting for a CA or a storage path on its own, so staging cannot be pointed
at production's directory, and any other value is a pair that does not exist —
Caddy refuses to load it. A trial certificate is therefore never in the
directory production reads, and cannot become the production certificate.

**Before any issuance**
- validation can succeed through the real public ports: 80 and 443 open to
  the internet in the network security group, with nothing else answering;
- Caddy's certificate storage is persistent — under `/var/lib/caddy` on the
  VM's disk, not a temporary filesystem (`findmnt -T /var/lib/caddy`) — and
  writable by Caddy (`sudo -u caddy test -w /var/lib/caddy && echo writable`).

**Issuance, in this order, with the two kept apart**
1. *Staging trial.* Add `QUANTDESK_CERTIFICATES=staging` to
   `/etc/quantdesk/caddy.env`, run the check above with `--require staging`,
   and start Caddy. `journalctl -u caddy` must show the certificate obtained
   from the staging directory; `curl -vk https://<hostname>/` must show a
   staging issuer. Browsers do not trust it: the site is not announced or
   used in this state.
2. *End the trial.* Stop Caddy. Remove the `QUANTDESK_CERTIFICATES` line. Run
   `./scripts/native/caddy/clear_staging_trial.sh`: it removes
   `/var/lib/caddy/quantdesk/staging-trial`, that one directory, written in
   the script in full. No setting, argument or environment variable can
   point it anywhere else. It searches for nothing and matches nothing by
   pattern, and does not look at production's directory or anything else
   Caddy keeps. It removes nothing unless it has positively established
   that Caddy is stopped — systemd reports the unit `inactive` or `failed`,
   and no `caddy` process is running — and that the directory and every
   directory above it is a real directory, not a link. If it cannot tell
   (systemctl missing or failing, a state it does not recognise, a check
   that errors), it stops. For `pgrep -x caddy` that means: exit 1, no
   process, is the only answer it proceeds on; exit 0 is a running Caddy;
   a missing `pgrep` or any other exit status is a look that did not
   happen, and nothing is removed. Then run the check with
   `--require production`.

   Both looks at Caddy — `systemctl` and `pgrep` — are point-in-time checks,
   not a lock. Nothing stops Caddy being started a moment after they pass, so
   Caddy must stay stopped for the whole cleanup, and keeping it stopped is
   the operator's job: the script does not start, stop or restart Caddy. Run
   it only as this step of the controlled after-market deployment procedure,
   never on its own.
3. *One production certificate.* Start Caddy once. `curl -v https://<hostname>/`
   (no `-k`) must succeed, and
   `openssl s_client -connect <hostname>:443 -servername <hostname> </dev/null | openssl x509 -noout -issuer -subject`
   must show a Let's Encrypt issuer that is not a staging one, for the exact
   hostname. Only then is the certificate step done.

**If production issuance fails: stop the go-live.** Do not switch CA, by
hand or automatically. Do not change the ACME settings to get past it. Do
not accept a certificate warning. Do not serve the site over plain HTTP or
bypass HTTPS. Do not force or repeat production issuance to "try again".
Read `journalctl -u caddy`, work out why, and bring it back for review.

**Renewal**
- Caddy renews by itself while it runs; `caddy.service` is enabled, and the
  storage above still holds the account and certificate after a reboot or a
  deallocation;
- what validation needed the first time is still there: the DNS name, the
  static IP, and 80 and 443 open to the internet.

A first certificate does not guarantee later renewals. It also does not show
that the name is free of rate limits shared with other users of the same
Azure domain: those depend on how the CA counts `cloudapp.azure.com` names,
which has not been verified here. With one CA there is no second one to
renew from if Let's Encrypt cannot.

**If the Azure-provided name cannot get a publicly trusted certificate
reliably — in staging, in production, or at a renewal — stop the deployment
and report that an owner-controlled hostname is required.**

## Going live

Only after the Phase 3B gate, with the market closed, the VIX close stored and
the change reviewed.

1. **Hostname.** Supplied, set on the public IP in Azure, and the DNS checks
   above passed. Nothing below starts without it.
2. **Deploy the reviewed commit** the usual way (bundle, `git pull --ff-only`).
   No API restart is needed for this change: the backend is not modified.
3. **Install Caddy 2.11.7**: `./scripts/native/caddy/install_caddy.sh`. It adds
   Caddy's apt repository, installs that release, and stops and disables the
   service. (The package starts a placeholder site on port 80 for the moment
   between install and stop; the port is still closed in Azure.) If a Caddy
   is already there it changes nothing, and stops if it is another version.
   Then run `./scripts/native/caddy/check_caddy_updates.sh` and record its
   answer.
4. **Install the site**: `./scripts/native/caddy/install.sh`. The first run
   creates `/etc/quantdesk/caddy.env` and stops. Set `QUANTDESK_HOSTNAME` and
   `QUANTDESK_BASIC_USER`; run
   `caddy hash-password --algorithm bcrypt --bcrypt-cost 14`, type the owner
   password at its prompt, and paste the hash into `QUANTDESK_BASIC_HASH`.
   Run `install.sh` again; "What install.sh does" below has its two parts.
5. **Open 80 and 443** in the Azure network security group (SSH stays as it
   is; 8000, 5173, 5433 and 6379 stay closed).
6. **Certificate**: the staging trial, the clean-up, then the one production
   issuance, as in the gate above. If production issuance fails, stop here.
   Otherwise leave it running with `sudo systemctl enable caddy`.
7. **Verify** from outside: `https://<hostname>/` shows no certificate
   warning and a Let's Encrypt production certificate for the exact
   hostname, asks for the sign-in and then shows the live dashboard;
   `curl -i https://<hostname>/api/journal` with the sign-in is 404; `http://`
   redirects; ports 8000 and 5173 do not answer from outside;
   `systemctl status 'quantdesk-*'` is unchanged, with one API process;
   `journalctl -u caddy` has no debug lines. In Safari, also the four checks
   under "Safari" above.
8. **Only then retire the Vite service**, once the public site has been used
   through a session: `sudo systemctl disable --now quantdesk-web`.

## Settings: five, and only five

`/etc/quantdesk/caddy.env` may set exactly these, each once:

| Setting | What it is |
|---|---|
| `QUANTDESK_HOSTNAME` | the site's public DNS name |
| `QUANTDESK_BASIC_USER` | the owner's sign-in name |
| `QUANTDESK_BASIC_HASH` | the bcrypt (cost 14) hash of the owner's password |
| `QUANTDESK_API_KEY` | the API's own key, added by the proxy to the stream |
| `QUANTDESK_CERTIFICATES` | absent for production, `staging` for the trial |

Nothing else is configurable for this deployment, on purpose: the ports are
80 and 443, the API is `127.0.0.1:8000`, the dashboard is served from
`/srv/quantdesk/web`, and the two certificate-storage directories are the two
named above. `install.sh` refuses a settings file that sets anything else —
a port, an upstream, a storage path, a CA, an unknown name — or sets one of
the five twice, and changes nothing when it does.

The Caddyfile does read a few more names from its environment
(`QUANTDESK_HTTP_PORT`, `QUANTDESK_HTTPS_PORT`, `QUANTDESK_UPSTREAM`,
`QUANTDESK_WEB_ROOT`, `QUANTDESK_ACCESS_LOG`, `QUANTDESK_STORAGE_ROOT`). They
exist so the tests can run this exact file on loopback ports in a temporary
directory. They are not deployment settings; each has the fixed production
value as its default, and the installer's refusal is what keeps them out of
the settings file. It checks the file when it runs: it is not a guard on a
file edited by hand afterwards.

## What install.sh does

Two parts, never mixed.

**Check — nothing on the machine is replaced.** In a temporary directory, in
this order, stopping at the first failure with "Nothing was changed":

1. Caddy is exactly the reviewed version (always first);
2. the settings file exists, holds only the five settings this site takes,
   each once, with no placeholder left;
3. the hostname is a public DNS name, not `localhost` or an address;
4. the sign-in name is set and the hash is bcrypt of cost 14;
5. the dashboard builds (and passes `build_web.sh`'s own search for secrets);
6. Caddy accepts the Caddyfile with the real settings (`caddy validate`, with
   its log file and storage pointed into the temporary directory, because
   loading a configuration creates them);
7. the effective certificate authority and storage are one of the two pairs;
8. the `caddy` user, `/etc/caddy`, `/etc/systemd/system` and `/var/lib/caddy`
   exist.

The one thing created before those are complete is the settings file itself,
the first time, from the template. It replaces nothing and the run ends there.

**Promote — only after every check has passed.** The prepared dashboard,
Caddyfile and service drop-in are first laid down beside their destinations
under `.new` names, then swapped in one at a time: what is there is renamed
to `.previous`, and `.new` takes its place. If a swap fails, the ones already
made are undone and the script says "Restored". It runs
`systemctl daemon-reload` and nothing else: Caddy is not started, restarted,
enabled or reloaded.

**Promotion is not fully atomic, and this is not a zero-downtime
deployment.** Each file is put in place by a rename, but the dashboard is two
renames — the directory being served is moved aside, then the new one is
moved in — and for a very brief interval between them the served directory
is absent. A request that arrives in that interval may get a transient 404.
The three swaps are also made one after another, not as one step. That is
accepted for an owner-only dashboard deployed in the approved after-market
window; a layout that switches in a single step was considered and not
adopted.

### `QUANTDESK_INSTALL_ROOT` is a test hook

`install.sh` reads one variable from its own environment that is not a
deployment setting: `QUANTDESK_INSTALL_ROOT`. It exists so that the tests can
run the real installer against a scratch directory.

- **In production it must be unset** — absent from the environment
  altogether, which is not the same as set to nothing. Check before running:
  `[ -z "${QUANTDESK_INSTALL_ROOT+set}" ] && echo unset`
  (or `unset QUANTDESK_INSTALL_ROOT`).
- If it is present it must name an existing scratch directory. Present but
  empty, `/`, a relative path, or a path that is not a directory or resolves
  to the real root is refused before anything is read or written. None of
  those is ever taken to mean production.
- Setting it changes the filesystem root the installer uses: every path it
  reads or writes under `/etc`, `/srv` and `/var/lib` becomes that path under
  the given directory.
- When it is set the installer says so, as its first line of output:
  `installing under <directory>`. If that line appears on the VM, stop.
- That line reports the variable. It does not prove isolation, and neither
  does anything else the script prints. What is and is not redirected:
  - redirected: the settings file, the dashboard, the Caddyfile, the service
    drop-in, their `.new`, `.previous` and `.before-quantdesk` neighbours, and
    the directories it checks for;
  - skipped: `systemctl daemon-reload`. With the hook set the installer does
    not call `systemctl` at all, and prints that it skipped it. That is
    decided by the variable alone, not by guessing what kind of machine or
    `systemctl` it has;
  - not under the root: its temporary working directory (from `mktemp`, in
    the system's temporary directory), and the commands it runs to look —
    `caddy` and `id` — which with the hook set on a real machine would still
    be the real ones. The tests replace those with stand-ins; the hook itself
    does not.
- With the hook unset, which is the only way production is installed, the
  installer runs `systemctl daemon-reload` after a successful promotion, as
  described above.


### If promotion fails

The script restores what it moved and stops. If it says `NOT FULLY RESTORED`,
or to go back to the previous deployment by hand at any later time, each of
the three has its predecessor beside it:

    sudo rm -rf /srv/quantdesk/web && sudo mv /srv/quantdesk/web.previous /srv/quantdesk/web
    sudo mv /etc/caddy/Caddyfile.previous /etc/caddy/Caddyfile
    sudo mv /etc/systemd/system/caddy.service.d/quantdesk.conf.previous \
            /etc/systemd/system/caddy.service.d/quantdesk.conf
    sudo systemctl daemon-reload

Check that a `.previous` exists before removing what it would replace (on a
first deployment there is none, and removing the new file is the whole
recovery). `.previous` holds one generation: the next successful run of
`install.sh` replaces it. The dashboard's files are served from disk, so that
restore shows at once; the Caddyfile and the drop-in take effect when Caddy
is next restarted, which is a decision for a person, not this procedure.

## Rolling back

To the SSH-tunnel model, at any point, without touching the desk:

1. `sudo systemctl disable --now caddy`
2. Close 80 and 443 in the Azure network security group.
3. If the Vite service was retired: `sudo systemctl enable --now quantdesk-web`.
4. Dashboard as before:
   `ssh -N -L 5173:127.0.0.1:5173 -L 8000:127.0.0.1:8000 azureuser@<vm>`,
   then `http://localhost:5173`.

`quantdesk-api`, PostgreSQL and Redis are never stopped by either procedure.
To remove the site entirely as well: delete `/srv/quantdesk`,
